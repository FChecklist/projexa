## B. GAPS — what the owner described that DOES NOT exist in code today

1. **There is no vector/RAG read at classification time.** The owner describes "a backend vector-RAG store holds input history and probable combinations; the software checks it." The classifier's four lookup tiers are all **exact string match or sha256 hash** — `phrase_map` (exact, `level0.ts:24`), `last_action` (`level0.ts:42`), structural regex (`level0.ts:107`), and `reuse_cache` (sha256, `reuse-cache.ts:67`). A grep for every vector/similarity primitive across `src/lib/pipeline/` returns two prose comments and zero executable calls. RAG exists in the codebase, but only on the chat-reply path (`chat-service.ts:733-735`), and its backing tables (`memory_records`, `memory_store`, `assistant_memories`) all hold **0 rows**.

2. **There is no confidence-based escalation decision.** The owner describes "logic to check CONFIDENCE of the work to be done and to ESCALATE to AI." What exists is the reverse: escalation to AI happens on a **boolean L0 miss** (`run-submission.ts:886`), and the only confidence number (`MIN_CONFIDENCE = 0.8`, `level1.ts:28`) is checked **after** the AI has already been called, to decide whether to keep its answer. No score is computed before the escalation decision anywhere on this path.

3. **There are not 3 live AI levels; there is 1.** The AI interface has exactly two methods (`adapter.ts:40-45`): L1 live in-request, and L2 **nightly batch only** (cron `30 10 * * *`). The model-registry enum is closed at two values (`schema.ts:12889`), and the DB holds exactly two rows. The 3-tier taxonomy the owner describes does exist as `PERCEPTION | REASONING | AUTHORITY` (`escalation-tier-catalog.ts:85`) but is **dead code** — a repo-wide grep finds zero importers, and the file's own header (`:21-23`) states it deliberately wires into nothing. There is no L3/AUTHORITY tier reachable from a user request.

4. **Nothing measures ERP-vs-AI usage on the live path, so 95/5 cannot be substantiated or refuted.** `l0HitRate`/`modelCalls` are computed in `runSubmission()` (`run-submission.ts:593`) but **only written to `console.info`** and never persisted — `compliance.submissions` has no such column. And the live typed path from PROJEXA does not go through `runSubmission()`; it goes through `submitForVerdict()` (`route.ts:214`), whose log line (`run-submission.ts:1202-1205`) **omits both fields entirely**. The AI usage ledger built for exactly this (`0524_r65_partd_ai_usage_ledger.sql`) is never written by any pipeline file and holds 14 stale rows from a different subsystem, all with `level = NULL`.

5. **Nothing enforces or gates on 95/5 — it exists only as an aspiration.** No constant, config row, or comparison encoding 95% / 5% exists anywhere in `C:\ct\ct\src` (30 candidate grep hits reviewed; all unrelated thresholds). The nearest thing, `ai-reduction-service.ts:87`'s `softwareCoverageRatio`, measures a **different subsystem** (`platform.task_capabilities`, 1 row) and has only **1 snapshot** (all-zero, dated 2026-08-01), so it cannot currently produce a ratio at all.

6. **"MULTIPLE TASKS" is implemented but has never fired in production.** `classifySubmission()` (`classify.ts:252`) returns `MULTIPLE_TASKS` correctly and the enum column exists, but live SQL shows **45 of 50 submissions have `classification = NULL` and all 5 populated rows are `TASK`**. Neither `MULTIPLE_TASKS` nor `CHAT_ONLY` has ever been recorded.

7. **The per-segment verdict array is discarded by the client.** The server goes to deliberate lengths to keep one verdict per segment and warns callers not to collapse it (`verdict.ts:72-74`, `tasks/route.ts:60-63`). The PROJEXA client contains **no reference to `verdicts` at all**, and its declared `verdict` field (`M24Shell.tsx:347`) is never read — the UI branches on `status` and renders only `verdict.missing[0]` (`M24Shell.tsx:2397`). So a mixed task+chat message is presented to the user as one outcome, which is the exact defect R53 was written to remove.

8. **"Builds the correct sequence of MODE + OPTIONS SELECTION" is not inference.** `deriveMode()` (`chain-mode.ts:28-34`) reads the UI's current chain segment id, not the user's text; the chain is derived *after* a function is resolved and rendered as an "Understood:" string. Nothing infers a mode or an options selection from the raw input.

9. **The reuse cache — the mechanism whose stated purpose is "don't call AI when software can determine the action" — has never served a single request.** `compliance.reuse_cache` = **0 rows** despite 50 submissions.

10. **The declared read-only classification endpoint is dormant.** `POST /api/classify` exists on both sides (`classify-only.ts`, `projexa/src/app/api/classify/route.ts:29`) and is the only surface that exposes `level`, `source`, `l0HitRate` and `modelCalls`, but no client code calls it, and the narrowing helper that would read it (`composer-turns.ts:145`) drops `source` and `level` and is itself uncalled outside tests.
